# Working in this repository

Apps for BMW iDrive 7 head units (MGU), published as a source for the
[MGU Store](https://github.com/robertnisipeanu/mgu-store). The owner adds this repository in the Store on
the car; the head unit downloads it at a commit, builds each app from source and installs the prebuilt
tools. Nothing here runs on your machine in production, and nobody can SSH into the car for you.

Read first: `README.md` (layout), the README of the app you touch, and `kit/CHANGES.md`.

## What the code runs on

| | |
|---|---|
| Apps | **Node.js 8.16.2** inside BMW's app platform, one process per app, under CPU and memory limits. |
| Tools | x86-64 Linux 4.14, **glibc 2.27**, loader `/lib/ld-linux-x86-64.so.2` (there is no `/lib64`), systemd, BusyBox. |
| Build on the unit | `kit/tools/build.py` under Python 3.12 with the standard library only, no network, as an unprivileged user. |
| Screen | 1920 x 720. Apps draw through the Store's Renderer (mgu-render); an app's page is 1600 x 520 logical px. |

Node 8 has no optional chaining, `??`, optional `catch` binding, `Promise.prototype.finally`,
`Array.prototype.flat`, `fs.promises`, `fs.mkdirSync(..., { recursive })`, `stream.pipeline`, global `URL`
(use `require('url').URL`), regex lookbehind or named groups. Destroying a stream with an error ends it
before the error shows there (see `rangeSource` in `apps/hrybak_youtube/net.js`). Run the tests under it:
`npm install node@8.16.2` in a scratch folder gives the binary.

## Rules that are not negotiable

- **No BMW SDK or firmware-derived file in the repository**, ever: no `oap-sdk/`, no built `dist/` package
  (a package built with an extracted SDK contains it), no interface catalog, nothing that identifies a car.
  `.gitignore` covers the usual ones; the tests build with a stand-in SDK they write and remove themselves.
- **An app must never exit or throw out of its start-up.** The platform wipes the data of an app that
  exits unexpectedly and uninstalls it the second time. Catch, log (`ctx.log`), show the problem on the page.
- **Nothing here has been run on a car unless a README says so.** Do not write that something works on the
  car because a test passes. Each app's README has a "What is not known yet" table: keep it true, and update
  it when the owner reports what the car did.
- **Anything that distracts a driver is parked-only by default** (the kit's `parked.js`, a `parkedOnly`
  setting that ships on), as the YouTube app does with its picture.
- **Tests never contact the services an app uses.** They run against a local stand-in
  (`test/hrybak_youtube/mock_youtube.js`). Asking the real service from a development machine is done only
  when the owner asks for it.
- **Ask the owner before** building a tool for the head unit in an automated session (it downloads and runs
  FFmpeg's build), before anything that touches sound devices by default, and before opening a pull request.

## Commits

- Author and committer are the repository owner (Hubert Rybak) and nobody else: set `git config user.name`
  and `user.email` to the owner's before the first commit, and ask if you do not have them.
- No co-author trailers, no tool or assistant attribution, no "generated by" lines: not in commit
  messages, pull request titles or descriptions, code comments or files.
- Say what changed and why, in plain sentences. One commit per coherent change; a rebuilt tool binary goes
  in the commit of the source change that needed it.

## Layout, and where a new app goes

```
apps/<id>/       app.json + main.js + other .js modules + icon.png (140 x 140, transparent) + README.md
native/<tool>/   a native tool: src/, build.sh, test/, README.md with its protocol
tools/<tool>/    the installable tool: built program, component.json, systemd unit, licences
test/<id>/       the app's tests (test_*.js) and their stand-ins
kit/             the idrive7-apps kit, copied; changes listed in kit/CHANGES.md
```

- The folder name under `apps/` **is the app's id**, with the `hrybak_` prefix (ids are global on a head
  unit). `mgu-repo.json` lists `apps/*`, so a new folder with an `app.json` is a new app in the Store; give
  it a `loggingId` of its own (four characters, `OAY1` is taken).
- `kit/tools/build.py` packs from the app folder: every top-level `.js` (`main.js` becomes the entry),
  `.wasm`, `LICENSE`, `NOTICE`, and **every subfolder as one data file** (`<name>.pack`). So no `test/` or
  `docs/` folder inside an app folder; `.md`, `icon.png` and other files are left out of the package.
- Apps share code only through `kit/runtime/` (copied into every package as `./kit/<file>`). A module a
  second app needs too (the YouTube app's `net.js` is the likely first) moves there, with a line in
  `kit/CHANGES.md`.
- Tools are listed in `mgu-repo.json` `tools`, and an app that needs one names it in `requires` there.
  `requires` is shared by every app under `apps/*`: when apps start to differ, give the ones that differ
  their own entry in `mgu-repo.json` (the Store's `docs/PUBLISHING.md` has the format).

## The kit

`kit/` is a copy of idrive7-apps' kit at the commit `kit/README.md` names, cut down to what the apps here
use. Prefer not to change it; when you must, keep the change small and add it to `kit/CHANGES.md`, which is
the list a later update from upstream is merged against. Upstream's README documents `app.json`, `ctx` and
the drawing calls.

What the YouTube app relies on, and a new app can copy:

- One `canvas` screen; the app draws its own tabs (`G.frame`) and pages, and everything pressable is a
  target (`cv.target(x, y, w, h, run, key)`): a tap runs it and the iDrive controller walks the targets.
  That only works where the kit runs the screen (`cv.own`: mgu-render with touch); otherwise draw a page
  that says what is missing (`limited()` in `apps/hrybak_youtube/ui.js`).
- Text that comes from outside the app (titles, names) is drawn with the fonts `ui` / `uib` and
  `{ literal: true }`; they cover accented Latin, Greek and Cyrillic. The Renderer's glyph atlas is shared
  by all apps and small: stay with the sizes already used (see the comment at the top of `ui.js`'s text
  helpers and `kit/tools/bake_wide.py`).
- Pictures and video: `ctx.media`, `cv.picture`, `cv.video`, and `cv.media` to ask what the frame's
  renderer can show.
- Internet: only through the Store's uplink, with names resolved by the DNS servers of its lease
  (`net.js`); `"internet": true` in `app.json`.
- Draw on changes, not every tick (`dirty` in `main.js`): the Renderer keeps the last frame.

## Native tools

- Source in `native/<tool>/`, built by its `build.sh`: `host` for tests (system libraries), no argument for
  the head unit (static dependencies, glibc 2.27 through `zig cc`, the unit's loader; the script checks the
  result). The head-unit binary is committed in `tools/<tool>/` because the Store installs committed files.
  **A change to a tool's source means rebuilding and committing that binary.**
- A tool that needs root for set-up starts as root and gives it up before reading any input, as
  `native/ytplay/src/main.c` does. Sockets for apps go in `/run/<tool>/`, group `tm_oap_app`, 0660.
- Set the core limit to 1 and list the program in `component.json` (`crashNames`, `recmgr`): a core dump or
  a stopped service the unit does not know restarts the whole head unit.
- A tool's protocol is documented in its README; change both together, and keep old requests working or
  bump the versions below.

## Versions

Cars update one component at a time. When you change something a car may already have:

- An app: `version` in `apps/<id>/app.json`.
- A tool: `version` in `tools/<tool>/component.json` (and the program's own, e.g. `YTPLAY_VERSION` in
  `native/ytplay/src/util.h`).
- An app that needs the newer tool: the tool's new version in `requires` in `mgu-repo.json`.

## Before you push

```sh
sh test/run.sh                           # everything, on this machine's Node
NODE=/path/to/node-8.16.2 sh test/run.sh # and on the head unit's
```

Both must end with `every test passed`. They need ffmpeg (with x264, libvpx, Opus and WebP encoders, for
the test videos), the FFmpeg and ALSA libraries with their development packages, and Python 3. When you
change how a page looks, look at it: `node test/hrybak_youtube/test_app.js --shots <folder>` writes each
page as a PNG.

New behaviour gets a test beside the others; a new app gets `test/<id>/` with at least a start-up test like
`test/hrybak_youtube/test_runtime.js`, which is what catches a tile that would say "Loading app" for ever.

## Writing

Comments and documentation describe how things are, not how they changed ("previously", "now" and "new"
do not belong in them). Say plainly what is unverified. Keep each README's claims to what the code does.
